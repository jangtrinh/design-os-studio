## 1. Summary and user story

Owner intent, as the controller's brief relays it (Jang, 2026-10-28; it is not a row of plan.md's rulings table): use the design:os CLI to build a proper, ontology-driven component registry that covers every element, component and screen, from primitive through semantic to composite. Then no AI that designs Studio UI can drift from the defined design system.

- As a design agent (Claude designer, Argon/agy, Grok), my brief carries the design system in tiers: tokens (primitive → semantic → component) and UI (element → component → composite → region → screen → flow). For each tier I know what exists, which tokens it uses, which kit node it came from and which Rust symbol draws it. A new screen is assembled from registered records and never invented.
- As the controller, CI tells me when the registry, the Rust kit and the token store disagree. It also tells me when a screen picks up a pattern T proposes to ban (3.3), such as an upper-case tag, a brand-filled selected tab or a gradient button. I do not have to find these by eye.

Outcome: every element, component, composite, region and screen of Studio's chrome has exactly one registry record, made with `ui registry register` on the sealed store. Every flow screen in `design/flow.json` maps to a record. Every theme colour name falls in exactly one declared map class. `scripts/check_ds_ontology_parity.py` checks the three links (registry ↔ Rust kit, chrome ↔ contract names, contract names ↔ store) and the measured absence and slot ratchets.

## 3. Behaviour rules

### 3.1 The ontology: two axes

**Token axis** (DTCG). Kit source: `_Primitives` → `1. Color modes` (whose subgroups include the component roles) plus the scale collections. The kit has no separate component collection (R9).

| Tier | Definition | Kit (Dark, R9) | Studio today | Studio after T (and after G1) |
|---|---|---|---|---|
| Primitive | context-free raw value, named by what it is | `_Primitives` 343 (Neutral, Orange, Red… 50–950; Base) | literal hex inside each role token; no primitive keys | `colors.ramp-<hue>-<step>` keys (5.4) added by G1; until then no primitive is addressable, and no UI tier may cite one |
| Semantic (role) | a meaning that aliases one primitive per mode | `1. Color modes` Background 28, Text 21, Foreground 19, Border 8, Effects 23; Radius 11, Spacing 17, Widths 12, Containers 3, Typography 32 | 77 store keys under Studio role names (`colors.surface`, `radius.radius-md`…), re-valued by A and B; 119 kit-role and Studio-only contract colour names (107 + 12): 30 mapped to a key by G01 after A, 21 sharing an existing key with the same value and role, 68 with no key yet (R36) | each Studio key aliases its primitive; a contract name whose value and role no key holds becomes a key named after its Studio constant (5.4: `BG_PRIMARY_SOLID` → `colors.bg-primary-solid`), and one whose value and role a key already holds binds that key (`BG_SECONDARY_HOVER` → `colors.surface-hover`) |
| Component | a role scoped to one component | `1. Color modes` subgroups Utility 134, Alpha 20, Components 20 (R9) | none in the store; `theme.rs` holds the badge, tile, slider and tooltip roles as Rust-only constants | `colors.badge-*` and `colors.tile-*` (the renamed `UTILITY_*` constants, 5.4), aliasing semantics |
| Composite (DTCG) | `typography`, `shadow` | 44 text styles and 26 effect styles, by name only (R2): styles, not variables | `typography.font-size-*` and `font-family-*` atoms only | `typography.text-xs` … composite tokens once S2 (Studio export) and G8 (`ds import`) exist; shadows stay out (alpha 0 in Dark, A rule 10) |

Reference rule (tokens): component → semantic → primitive, one hop at a time (18 kit semantics alias another semantic, which is allowed inside the semantic tier). Rust `theme.rs` constants are views of semantic or component tokens, never of primitives, except the exempt classes (5.3).

**UI axis.**

| Tier | Definition | Kit counterpart | Studio examples (record names, 5.1) |
|---|---|---|---|
| Element | indivisible visual atom with no interaction of its own and no child records | FOUNDATIONS (icons, effect styles), the `_`-prefixed parts | `Divider/Hairline`, `Focus/Ring`, `Icon/Glyph`, `Status/Dot`, `Menu/Separator`, `Menu/Shortcut` |
| Component | a self-contained widget with its own states, built from elements | BASE COMPONENTS | `Button/*`, `Input/*`, `Select/Trigger`, `Menu/Item`, `Tabs/Pill`, `Tree/Row`, `Badge/StatusCount`, `Tooltip/Default` |
| Composite (pattern) | a reusable arrangement of two or more components | APPLICATION COMPONENTS | `Menu/Panel`, `Dialog/Modal`, `Dialog/CommandPalette`, `Toast/Default`, `Section/Header`, `Card/FileThumbnail` |
| Region | a fixed layout zone of the Studio window that hosts composites; layout frozen by R1 | none in the kit (Studio's own frame) | `Navigation/TopTabBar`, `Navigation/LeftRail`, `Panel/LeftLayers`, `Panel/RightInspector`, `Panel/AgentTerminal` |
| Screen | one window state: a set of regions on screen at once | APPLICATION EXAMPLES | `Screen/Home`, `Screen/EditorDesign`, `Screen/EditorPrototype`, `Screen/EditorDev`, `Screen/Present` |
| Flow | transitions between screens and their states | none | `design/flow.json` (16 IA nodes, 131 transitions) |

Reference rule (UI), enforced by check P4: a record names only records of its own tier or a lower one (element < component < composite < region < screen), with no cycles; a screen also names the composites that float above its regions (dialogs, palettes, toasts); flows name screens. Why same-tier nesting is allowed: C's anatomy puts the header pattern (`Panel/Header`) inside `Dialog/Modal` and `Popover/Panel` and segmented tabs inside the command bar, so a strictly-lower rule would contradict C. No record of any tier names a primitive token. In Rust, a region or surface file paints through kit calls (C) and theme constants (A, B), never through raw literals (A's colour ratchet, B's spacing ratchet).

### 3.2 How each concept maps onto the CLI today (no sidecar JSON; owner: use the CLI)

| Concept | Carried by (CLI field) | Rule |
|---|---|---|
| Tier | `--category` ∈ {`element`, `component`, `composite`, `region`, `screen`} | category is the one free field `ds context` shows agents; the functional family lives in the name's first segment (`Button/…`, `Menu/…`) |
| Composition | `--markup`, generated from the record's `composes` list: `<div data-ds="<Name>">` holding one `<div data-ds="<child>"></div>` per child, in table order (`Button/*` stays a literal wildcard meaning any record of that family) | the gate parses `data-ds` and checks the reference rule; markup is never an implementation |

The kernel stores both as capitalised variants (`State=Active`, `statesToVariants`), and P5 compares that stored spelling. Records C does not cover declare no `--states` |
| Tokens | `--tokens`: store paths that resolve in the sealed store (`register` refuses others) | a record binds the key of each colour or radius it paints after A and C, only when the key's value equals that constant's value (and, for colours, the key carries the same role). | Provenance and binding | `--description`: one purpose sentence, `<Tier> of Studio's chrome, specified in spec <owner>.`, then one line `tier=<t>; rust=<sym>[,<sym>]; rust_status=<exists\|new-in-C\|new-in-D\|new-in-K>; today=<file>::<fn> or <file>:<lines>; paints=<CONST,…>; pending=<CONST,…>; spec=<owner>; flow=<id>[,<id>]; composes=<names>`. | Screens and flows | screen records (category `screen`), plus `design/flow.json`, whose screen ids appear in exactly one record's `flow=` list (comma-separated; `Screen/Home` carries six) | `ui flow lint` stays the flow gate; the parity script checks the id ↔ record map and that each artifact exists |
| Lifecycle | not expressible (no `status` or `deprecated` on register) | G3; until then a retired record keeps its name and its description starts `retired:` |
