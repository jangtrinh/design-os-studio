## 1. Summary and user story

As a designer using Studio, every button, field, menu, row, toggle and dialog looks and behaves like one Untitled UI dark component in each of its states, so the app reads as one system and focus is always visible. As an implementer of specs D–K, I call one kit function per widget kind with a size and a state and get the Untitled look; I never pick a colour, radius or font in a surface file.

**S3 State model.** Six table states, Default, Hover, Pressed, Focused, Disabled and Selected, plus **Loading** for buttons. Precedence: Disabled > Loading > Pressed > Selected > Hover > Default. Focused is additive: the ring is drawn on top of whichever look applies.
- Hover follows the pointer only.
- Pressed (pointer down) is derived because the kit has none: brand fills go to Orange-600, the destructive solid fill to Red-800 `#991B1B` (`BG_ERROR_SOLID_PRESSED`), the secondary destructive border to `border-error` `#F87171` (it has no solid fill), neutral fills to `bg-quaternary` `#404040` (contract `BG_PRESSED`; only `text-primary`/`text-secondary` text and icons at `fg-quaternary_hover` or brighter sit on it).
- Loading (kit, buttons only): the Hover look, a 16 px spinner (`Loading/Inline` arc) before the label, no pointer response. No Studio surface starts an async button today, so the tables carry no Loading column; a surface spec that needs one uses this rule.
- Selected + Hover keeps the Selected fill and takes the hover text and icon colour.
- Focus traversal: `widgets/field_tab.rs` stays as shipped. While a field holds focus, Tab and Shift+Tab walk fields only; when no field holds focus, egui's Tab walk reaches buttons, tabs, toggles, checkboxes, swatches and rows, and each draws the S4 ring while it holds focus. Text fields show their focused border whenever they hold focus, pointer or keyboard (kit Input Focused).

**S4 Focus ring (FACT, section 2).** A 2 px `focus-ring` `#F97316` band from 2 px to 4 px outside the control, outer radius = control radius + 4, with the 2 px gap left showing the surface. Text fields and selects draw no ring: their border becomes 2 px `border-brand` `#FB923C`. Destructive buttons, solid and secondary, ring in the kit's `focus-ring-error` `#EF4444` instead (both kit hierarchies carry `Focus rings/focus-ring-error-shadow-xs-skeuomorphic`; 5.26:1 on `#0A0A0A`). ## 8. Edge cases

- **Concentric radius.** Settled by R5 and R8.5: menu items are radius 8 at inset 8 inside a 16 menu (16 − 8 = 8), segment tiles 6 inside an 8 control with a 2 inset. The kit's own 6-in-8 pills are not used.
- **Focus ring clipping.** The ring sits 2–4 px outside the control. Inside a scrolled or clipped panel it is drawn with the parent clip widened by 4 px; at a panel edge it is clipped, never shifted.
- **Pixel snapping.** At 1x a 2 px ring is two device pixels; at 1.5x and 2.25x (Fold 7) the ring rect is snapped to physical pixels like `snap_y` (`widgets/mod.rs:143`).
- **Focus versus pointer.** The ring shows for keyboard focus (Tab when no field holds focus, S3; arrow keys where a widget has them). A text field shows its focused border whenever it has focus, including after a click, because that is the kit's Input Focused state.
- **Disabled + focused** cannot happen: a disabled control is not focusable. **Selected + hover** uses the Selected look with the hover text colour.
- **Mixed values** ("Mixed" in number fields) use `text-placeholder` like a placeholder.
- **Destructive** buttons use the error ramp (`bg-error-solid`), never the brand.
- **Canvas exceptions**: component cyan, selection blue, guide red and Dev emerald stay as in plan.md; a component layer's row icon and label in Layers keep `canvas-component #06B6D4`.
- **Light canvas labels** (`TEXT_ON_LIGHT_CANVAS*`) are canvas overlays, not widgets; unchanged.
- **Hover on a filled surface.** A widget on `bg-secondary` uses the `_hover` of that surface (`bg-secondary_hover #262626`), never `bg-primary_hover #171717`, which would be invisible there (rule S6).
