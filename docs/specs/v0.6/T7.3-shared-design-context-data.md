## 1. Summary and user story

As the Inspect panel and as the MCP server, we compute box model, variables used, component properties
and annotation values with one implementation, so an agent sees exactly what a developer sees in Dev
Mode, and a fix lands in both at once.

## 2. Current state (FACT)

- The Inspect panel's pure data lives in designos-app: `BoxModel`/`box_model`
  (`crates/designos-app/src/dev/data.rs:9-19`), `resolve_in_mode` (`data.rs:88`), `variables_used`
  (`data.rs:109`), `format_value` (`data.rs:142`), `component_rows` (`data.rs:161`),
  `applicable_properties` (`data.rs:198`), `property_value` (`data.rs:214`). It imports
  `crate::widgets::fmt_num` (`data.rs:4`), whose format is 2 decimals with trailing zeros trimmed
  (`crates/designos-app/src/widgets/mod.rs:229-237`).
- Callers: `crates/designos-app/src/dev/sections.rs:374`, `:489`, `crates/designos-app/src/panels/inspect.rs`,
  and tests in `crates/designos-app/src/shell/tests/dev.rs:246-315`.
- The code-language list exists twice: app `Language` (7 entries, `crates/designos-app/src/dev/mod.rs:18-55`)
  and the MCP `generate_code` match (8 strings including `svg`, `crates/designos-mcp/src/engine.rs:116-126`).
- designos-export already depends only on designos-doc and designos-render
  (`crates/designos-export/Cargo.toml:11-12`), and has its own `num` with 3 decimals
  (`crates/designos-export/src/util.rs:6-17`) — a different format from `fmt_num`.

## 3. Behaviour rules

1. Move, do not rewrite: every function listed above moves to `designos_export::design_context`
   with identical signatures and bodies; `fmt_num` moves to `designos_export::util::fmt_num` with its
   exact current format (2 decimals), and `widgets::fmt_num` re-exports it. `util::num` (3 decimals,
   used by codegen) is unchanged; the two formats stay distinct on purpose (UI vs code output).
2. designos-app keeps `dev/data.rs` as a thin `pub use designos_export::design_context::*;` for one
   release so call sites compile unchanged; then call sites import from designos-export directly and
   the shim is deleted in the same PR if the diff stays small.
3. One language list: `designos_export::language::CodeLanguage` with `ALL` in the Dev Mode dropdown
   order, `label()` (UI), `id()` (MCP string: `css`, `tailwind`, `swiftui`, `uikit`, `compose`,
   `android-xml`, `react`), `generate(doc, node, opts)`. The app's `Language` becomes a type alias or
   wrapper; the MCP `generate_code` resolves the string through `CodeLanguage::from_id` and keeps `svg`
   as a separate export target (not a code language). The MCP error lists `CodeLanguage::ALL` ids plus
   `svg`, generated, never hand-written.
4. No behaviour change: Inspect panel output is byte-identical (same strings), MCP outputs are
   identical.

## 8. Edge cases

1. `fmt_num(-0.001)` returns `"0"` in both locations (current behaviour preserved).
2. `resolve_in_mode` with an alias cycle: unchanged behaviour (moved verbatim); covered by existing
   tests.
3. Functions that used app-only types (widgets): none besides `fmt_num`; the compiler proves it.
4. Language dropdown order must stay Figma's grouping (comment at `dev/mod.rs:30`).
5. React's Tailwind toggle (`react_tailwind`) stays an option of `generate`.
