## 1. Summary and user story

As a maintainer and as an agent, I can trust the published tool list: one generated source says which
tools exist, the docs quote it verbatim, a test fails when the list changes without regenerating, and a
matrix shows how each tool of Figma's MCP server maps to a studio tool, a task, or a named exclusion.

## 2. Current state (FACT)

- The live tool list is `crates/designos-mcp/src/server.rs:620-631` (engine tools from
  `crates/designos-mcp/src/engine.rs:705-829` plus four session tools); the stdio test asserts 22
  (`crates/designos-mcp/tests/stdio.rs:12`).
- `designos_query_xpath` and `designos_lint` are dispatched (`engine.rs:307`, `engine.rs:350`) but not

- No parity matrix exists.

## 3. Behaviour rules

1. Every dispatched tool must be declared; a test enumerates the match arms' names (a `const
   DISPATCHED: &[&str]` kept beside `Engine::call`) and compares them with `tools()`; mismatch fails.
   This task declares `designos_query_xpath` and `designos_lint` with their current schemas (E15-9 and
   E15-17 extend them later).
2. Snapshot: `tests/snapshots/tools.json` holds, per tool, name, description, input schema, output
   schema (when E15-5 lands) and annotations. `tools_snapshot` serializes `tools()` canonically and
   compares. On mismatch the failure message prints the command to regenerate
   (`cargo run -p designos-mcp --bin gen-tool-docs`).
3. Generated docs: the generator rewrites the blocks between `<!-- designos-mcp-tools:begin -->` and
   `<!-- designos-mcp-tools:end -->` in `README.md`, `CLAUDE.md` and `skills/design-os-studio/SKILL.md`
   with a table (name, one-line description, read-only flag) and the count. The snapshot test also
   checks those blocks are current, so prose counts like "29 tools" cannot drift again.
4. Parity matrix: `parity/figma-mcp-parity.json`, one row per Figma MCP tool (Figma's core tools plus
   its 9 Weave tools; 41 rows at filing time) taken from Figma's public MCP documentation on the day of
   implementation, with the doc URL and retrieval date in the file header:
   ```json
   {"figma_tool":"get_screenshot","status":"implemented","studio_tool":"designos_get_screenshot"}
   {"figma_tool":"generate_image","status":"task","task_id":"T7.37","note":"through the agent CLI (R4.13)"}
   {"figma_tool":"<weave tool>","status":"excluded","reason":"hosted service (R4.14)"}
   ```
   `status` ∈ `implemented | task | excluded`; `implemented` requires `studio_tool` to exist in
   `tools()`; `task` requires a task id that exists in the roadmap; `excluded` requires a reason that
   cites an owner ruling. A test validates those rules.
5. Owner rulings applied in the matrix: R4.13 (`generate_image` goes through the agent CLI; studio side
   is `upload_assets`, T7.37), R4.14 (Weave and other hosted tools are named exclusions),
   `send_code_to_figma` maps to T7.14.
6. A generated `docs/mcp-parity.md` renders the matrix as a table (same generator).

## 8. Edge cases

1. A tool renamed with an alias kept for compatibility (`export_fig_file`, `query_nodes`,
   `check_design`, `engine.rs:297`, `307`, `350`): aliases are dispatched but not declared; the
   dispatch test treats them as aliases listed in `const ALIASES`.
2. Figma docs change after filing (tool added): the matrix row count is whatever the docs list on the
   retrieval date; the test checks consistency, not a fixed 41.
3. A `task` row whose task later ships: the test fails once the studio tool exists but the row still
   says `task` (status must be updated to `implemented`).
4. Descriptions containing markdown pipes: escaped in the generated tables.
5. Per-tool enable list (E15-15) disables a tool: the snapshot reflects the full catalogue; enable
   state is runtime configuration, not part of the snapshot.
