# E15-24 Generate large deterministic test documents from open kits

- Issue: #612 (task E15-24, epic #585, M / P0)
- Spec base: `main` at `767acf9`.
- Files: `crates/designos-eval/src/gen/{mod.rs,profile.rs,kit.rs,build.rs,screen.rs,tests.rs}` (new), `crates/designos-eval/src/gen/kits/{shadcn.toml,carbon.toml}` (new), `crates/designos-eval/src/gen/budgets.toml` (new).

## 1. Summary and user story

As the team, we want edit-task fixtures that are big (10k, 100k and 1M nodes), realistic (pages, components, instances, variables with modes, auto layout, text) and entirely ours, regenerated byte for byte from a seed, so S3 can test editing large files without any client file.

## 2. Current state

- FACT: no generator exists. The large benchmark used for performance work is a client file (CLAUDE.md §3, "VSF - PCP.fig"), which the owner bans from the eval.
- FACT: the document model holds nodes in a `BTreeMap<NodeId, Node>`, pages in `Vec<NodeId>`, variables and collections in `BTreeMap`s (`crates/designos-doc/src/lib.rs:147-162`), so serialisation order is stable.
- FACT: `apply_spec` builds subtrees from `NodeSpec` (`crates/designos-doc/src/spec.rs:360`); E15-1 adds instances and E15-3 variable references.
- FACT: open kits allowed by licence: shadcn/ui (MIT) and IBM Carbon (Apache-2.0), recorded in E15-23.

## 3. Behaviour rules

1. **Inputs:** `seed: u64`, `profile` (name or file), `kit` (`shadcn` | `carbon`), `nodes` target (10_000 | 100_000 | 1_000_000 or any value ≥ 1_000).
2. **Kit definition** (`kits/shadcn.toml`): our own re-creation of the kit's tokens (colour roles with Light/Dark values, radius, spacing, type steps) and component structures (Button with Variant × Size, Input with State, Card, Badge, Avatar, Table Row, Nav Item, Tab, Dialog, Select, Checkbox, Switch) described as NodeSpec templates with slots and `var:` references. No file is copied from the upstream repositories; attribution text comes from the register.
3. **Profile** fields with defaults:
   - `pages = clamp(nodes / 30_000, 2, 40)`;
   - `instance_ratio = 0.55` (share of nodes inside instances);
   - `variable_coverage = 0.75` (share of bindable properties bound, E15-26 definition);
   - `auto_layout_ratio = 0.85` (share of multi-child frames with auto layout);
   - `text_ratio = 0.30` (share of text nodes);
   - `modes = ["Light", "Dark"]`;
   - `screens_per_page`: derived so the node target is met.
4. **Construction order** (fixed): document → kit variables and collections → component page with every kit component and variant → for each page in order, screens built from a screen grammar (§3.5) until the page's node quota is used → final pass that adjusts the last screen to land exactly on the node target (±0.5%).
5. **Screen grammar.** A screen is a 1440×900 or 390×844 frame (chosen by RNG, 70/30) with a header, optional sidebar, and 2–6 sections; each section picks a pattern (card grid, table, form, list, stat row) and fills it with instances of kit components plus ad-hoc frames and text so the profile ratios are met. Text content comes from a fixed word list compiled into the crate (our own, no third-party corpus), chosen by RNG.
6. **Determinism.**
   - The only randomness is xoshiro256** seeded through SplitMix64 from `seed` (SC-7). Every random choice draws from one stream in construction order.
   - Node ids are allocated sequentially from 1. No wall-clock time, host name or path enters the document.
   - Output is the native `.designos` serialisation; maps are ordered; floats are written by `serde_json`'s shortest round-trip formatter. AC1: two runs with one seed produce identical bytes.
   - The document's `name` is `gen-<kit>-<nodes>-<seed>` and every generated file has a sidecar `<name>.profile.json` carrying `generator: "designos-eval gen <version>"`. E15-23's ban check recognises generated files by the name prefix plus the sidecar. No document format field is added.
7. **Profile verification (AC3).** After generation the generator measures the actual `instance_ratio`, `variable_coverage` (E15-26 `token_coverage` over the whole document), `auto_layout_ratio` and node count, and fails if any is off by more than ±0.02 (ratios) or ±0.5% (nodes). The measured values are printed and stored next to the file as `<name>.profile.json`.
8. **Budgets (AC2).** `budgets.toml` records, per node target, the time to load the file with `designos-doc` and to render page 1 at scale 0.1 headless on the CPU path, measured on the CI macOS runner when the task lands. A test regenerates the 1M file (release build, `--ignored` group run in CI nightly) and fails when either time exceeds 1.5× the recorded value. Initial targets to beat: load ≤ 20 s, render ≤ 15 s, peak RSS ≤ 6 GiB for 1M nodes.
9. **Caching.** Generated files go to the user cache (`designos-eval/gen/<kit>/<nodes>/<seed>.designos`) and are reused when their profile file matches; they are never committed (1M nodes is hundreds of MB). Tasks refer to them as `start = "gen:<profile>:<seed>"` (E15-25).

## 4. Data model / schema

```toml
# profile file (optional; built-in "default" equals the defaults above)
name = "default"
kit = "shadcn"
nodes = 100000
instance_ratio = 0.55
variable_coverage = 0.75
auto_layout_ratio = 0.85
text_ratio = 0.30
modes = ["Light", "Dark"]
```

```rust
pub struct GenProfile { pub name: String, pub kit: KitId, pub nodes: u64, pub instance_ratio: f64,
    pub variable_coverage: f64, pub auto_layout_ratio: f64, pub text_ratio: f64, pub modes: Vec<String> }
pub fn generate(profile: &GenProfile, seed: u64) -> Result<(Document, MeasuredProfile), GenError>;
pub enum GenError { ProfileMissed { metric: String, wanted: f64, got: f64 }, KitInvalid(String), TooSmall }
```

## 5. Contracts

`designos-eval gen --kit shadcn --nodes 100000 --seed 42 [--profile file.toml] [--out path] [--check]`:
- prints the output path and the measured profile JSON;
- `--check` regenerates in memory and compares bytes with the cached file (exit 1 on mismatch);
- exit 2 for invalid profiles (`nodes < 1000`, ratios outside 0–1).

## 6. File-format mapping

Native `.designos` only. A `--fig` flag also writes a `.fig` through `designos-fig`'s exporter for import-path tests; it is not used by S3.

## 7. UI

None.

## 8. Edge cases

1. Ratios that cannot be met together (for example `instance_ratio = 0.95` with `text_ratio = 0.6`): `ProfileMissed` naming the metric, not a silent best effort.
2. Node target below one screen: `TooSmall` with the minimum (1,000).
3. Platform differences in float formatting: avoided by never computing layout-dependent floats in the generator; positions come from auto layout run by `designos-doc` after construction, which is part of the deterministic engine. A test compares macOS and Linux CI outputs by SHA-1.
4. A kit change alters output: the kit file's SHA-1 is part of the profile file, so cached files are regenerated.
5. Out of memory on small runners: the 1M case runs only in the nightly job on the macOS runner.

## 9. Non-goals

- Visual quality of generated screens (they are realistic in structure, not polished).
- Using any third-party file directly.

## 10. Test plan

Seam: `cargo test -p designos-eval gen` (10k and 100k by default; 1M in an ignored test for the nightly job).

Fail-before: the module does not exist.

| Test | Input | Expected |
|---|---|---|
| `same_seed_same_bytes` (AC1) | generate 10k seed 7 twice | identical bytes (SHA-1 equal) |
| `different_seed_differs` | seeds 7 and 8 | different SHA-1 |
| `profile_is_met` (AC3) | 100k default | measured ratios within ±0.02, nodes within ±0.5% |
| `one_million_opens_within_budget` (AC2, ignored, nightly) | 1M default | load and render times ≤ 1.5× `budgets.toml` |
| `generated_file_is_recognisable` | any | name starts with `gen-`; sidecar carries `generator` |
| `kit_has_no_literal_values` | shadcn and carbon kits | every visual property in component templates is a `var:` reference |
| `cross_platform_hash` | 10k seed 7 | SHA-1 equals the value recorded from the macOS job |

Visual evidence: terminal capture of generation with the measured profile, and a CPU render of one generated screen.

## 11. Performance budgets

- 100k generation ≤ 20 s release build; 1M ≤ 4 min, peak RSS ≤ 6 GiB.
- Hashing for checks streams bytes; no extra JSON copies of the document (CLAUDE.md §4.1 spirit).

## 12. Dependencies and build order

- Needs E15-1 (#586), E15-3 (#588), E15-25 (crate and RNG), E15-23 (kit licences) and E15-26 (#614; AC3 measures `variable_coverage` with E15-26 `token_coverage`, so that metric must exist first).
- Unblocks E15-29 (S3) and the S2 design-system libraries (E15-28).
