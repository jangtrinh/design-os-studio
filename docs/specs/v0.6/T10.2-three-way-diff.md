## 1. Summary and user story

As the merge engine (and the branch review UI later), I compute what changed between a common base and
two descendants (main and a branch): adds, removes, moves and property changes for every layer, plus
styles, variables, collections and component definitions, and I report a conflict on a layer only when
both sides changed the same property differently.

## 2. Current state (FACT)

- Component definitions live on component nodes (`ComponentLink.props`, `slot_configs`,

- A zero-allocation streaming hash pattern exists for documents (`doc_hash` with `HashSerializer`,

## 3. Behaviour rules

### 3.1 Inputs and identity

`diff3(base: &Document, ours: &Document, theirs: &Document) -> Diff3`. Nodes are matched by `NodeId`
(T10.1 guarantees branch copies keep ids). Styles by key, variables and collections by id.

### 3.2 Property groups (the unit of change and conflict)

`name`, `visible`, `locked`, `opacity`, `blend`, `transform`, `size`, `fills`, `stroke`, `effects`,
`corner_radii` (+ `corner_smoothing`), `constraints`, `layout_child`, `mask`, `style_refs`, `variables`
(bindings and modes), `component` (link, overrides, props, values, slots), `prototype`, `dev`,
`export_settings`, `kind` (type change), `text.content`, `text.style` (style + runs + lists + paragraph),
`frame` (clip, auto layout, grids), `vector` (paths, network), `plugin_data`, `other` (remaining fields,
compared as one group). `parent+index` is the `position` group.

### 3.3 Classification per node, per side (versus base)

- `Added` (absent in base), `Removed` (absent on that side), `Moved` (parent changed, or index changed
  among siblings that exist on both base and that side), `Changed { groups }`.
- Index moves are computed with a longest-common-subsequence over sibling ids present on both sides, so
  inserting one sibling does not mark all following siblings as moved.

### 3.4 Conflicts (per layer, R5.18)

A layer conflicts when, for the same node:
- both sides changed the same property group to different values;
- one side removed it and the other changed any group or added children under it;
- both moved it to different parents (or different positions under the same parent);
- both added a node with the same id (possible since both allocate ids from the same counter) — an
  `IdCollision`, resolved by remap in T10.3, not shown as a user conflict.
Same change on both sides (equal values) is not a conflict. A `Conflict { node, groups, kind }` lists
every conflicting group of that layer so resolution is per layer.

### 3.5 Non-node entities

Styles, variables, collections, flows and comment threads: `Added / Removed / Changed` per key with the
same conflict rule (both changed differently, or delete vs change). Comment threads diff by thread id
and message ids (merge of threads is T10.10; this task only reports).

### 3.6 Algorithm and cost

1. For each document, compute per-node 64-bit hashes with a streaming hasher over the node's
   serialisable fields (no JSON strings), in parallel chunks on a worker thread pool.
2. Nodes whose hashes are equal across the relevant pair are unchanged; only differing nodes get
   group-level comparison (`PartialEq` per group).
3. Moves use parent ids from the nodes plus LCS on children lists of changed parents only.
Runs entirely off the UI thread; the UI receives the finished `Diff3`.

## 8. Edge cases

1. Node type changed on one side (frame → component via "create component"): `kind` group change; with
   a concurrent `fills` change on the other side → no conflict (different groups) unless the other side
   also changed `kind`.
2. Page added on both sides with different ids: two adds, no conflict.
3. Instance re-synced from a changed main component on one side: the mirror changes are `Changed`
   groups on mirror nodes; conflicts there are reported on the mirrors and grouped under the instance in
   the stats.
4. Reordering only (z-order) on both sides differently: `position` conflict.
5. Floating-point noise from relayout (transform differing by < 0.001): treated as equal (tolerance
   1e-3 on transform and size components) to avoid spurious conflicts.
6. Variable value changed in different modes on each side: not a conflict (different mode keys are
   separate values).

## 9. Non-goals

- Applying merges (T10.3), text-level (character) merges inside one text node.

## 11. Performance budgets

Large fixture (112,474 scene nodes; CI synthetic equivalent) with 1% edits per side: ≤ 1.5 s on a worker
pool, ≤ 500 MB peak extra memory (three documents are already in memory; the diff adds hashes and change
maps only). The full benchmark (1,082,324 nodes) is recorded locally. Never on the UI thread.
