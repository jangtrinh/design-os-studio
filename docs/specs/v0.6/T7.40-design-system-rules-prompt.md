## 1. Summary and user story

As an agent connected to a file, I can (a) run the `create_design_system_rules` prompt to get a rules
document generated from this file's variables (with code syntax), styles and components, naming where
every token comes from, and (b) call `designos_get_guidelines(topic)` to read our own design guides
per surface and the parameterised style archetypes.

## 3. Behaviour rules

### 3.1 Prompt `create_design_system_rules`

- Arguments: `scope` (`file` default, or `page:<id>`), `platform` (`web` default, `ios`, `android`),
  `max_tokens` (default 8,000).
- Returns one user message whose text is: a short instruction to save the rules into the user's code
  repository (e.g. a rules file the agent CLI reads), followed by the generated rules document in
  markdown:
  1. Token sources: one section per variable collection (and per enabled library collection), each
     with its origin (`This file` or `Library: <name> v<version>`), modes, and a table
     `name | type | value per mode | code syntax (<platform>)`. A variable without code syntax prints
     the A5 sanitized form.
  2. Text, colour and effect styles with origin and values.
  3. Components: name, origin, description, variant properties with options, slots with recommended
     components.
  4. Usage rules generated from the data: "use `<code syntax>` instead of literal `<value>`" for each
     colour and number token; the spacing and type scales (E15-11 scale sources).
- Truncation: when over `max_tokens` (estimated as chars / 4), lower sections are cut with an explicit
  marker `… truncated: <n> more tokens in <section>` (never silent). Every token line names its source
  (acceptance 2).

### 3.2 Tool `designos_get_guidelines`

- `topic`: one of the registered topics; `designos_get_guidelines()` with no topic returns the topic
  list with one-line summaries.
- Topic kinds:
  - `design-system`: the same generated document as the prompt (for clients without prompt support);
  - surface guides: `code`, `design-system-guide`, `landing-page`, `mobile-app`, `slides`, `table`,
    `tailwind`, `web-app`;
  - `archetypes` (list) and `archetype:<id>`: prose brief plus typed parameters (4 font slots, a
    role-keyed palette such as `surface.primary`, `accent.*`, roundness, elevation, imagery);
  - `rules`: added by E15-15.
- Content source (one source of truth, E15 link): guide prose and archetype briefs are data files under
  `crates/designos-mcp/guidelines/` (`surfaces/<topic>.md`, `archetypes/<id>.toml`), embedded at build
  time with `include_str!`. The files are authored by part-2 tasks E15-21 (surfaces) and E15-18
  (archetypes); this task ships the loader, the schema validation and the registry. Until a file
  exists, its topic returns `TOPIC_NOT_AVAILABLE` naming the providing task, and the topic list marks
  it `available: false` (no placeholder prose, no fake content).
- Archetype parameter schema is validated at build time (a unit test parses every archetype file
  against the typed schema); E15-19 compiles them with `designos_apply_style`.

## 4. Data model / schema changes

- `ArchetypeFile { id, name, brief, fonts: [FontSlot; 4], palette: BTreeMap<String, String>,
  roundness: Roundness, elevation: Vec<ShadowSpec>, imagery: String }` (TOML, serde,
  `deny_unknown_fields`). Final field list is owned by E15-18; this task defines the loader generically
  over E15-18's struct once it exists and, before that, validates only `id`, `name`, `brief`.
- Surface guide file: markdown with front matter `title`, `summary`, `applies_to`.
- No document change.

## 5. Contracts

Prompt (MCP `prompts/list`, `prompts/get`):

```json
{"name":"create_design_system_rules","description":"Generate design-system rules from this file's variables, styles and components, naming every token source.",
 "arguments":[{"name":"scope","required":false},{"name":"platform","required":false},{"name":"max_tokens","required":false}]}
```

Tool `designos_get_guidelines` (`readOnlyHint:true, idempotentHint:true`):

```json
{"type":"object","additionalProperties":false,"properties":{
  "topic":{"type":"string"},
  "platform":{"enum":["web","ios","android"],"default":"web"},
  "max_tokens":{"type":"integer","minimum":500,"maximum":25000,"default":8000}}}
```

Output: `{"topic":"design-system","content":"# Design system rules ...","truncated":false,
"sources":["This file","Library: Brand kit v4"]}`; topic list:
`{"topics":[{"id":"landing-page","summary":"...","available":false,"provided_by":"E15-21"}]}`.

Errors: `UNKNOWN_TOPIC` (`valid_options` = topic ids), `TOPIC_NOT_AVAILABLE`, `INVALID_ARGUMENTS`.

## 8. Edge cases

1. File with no variables or styles: sections say `No variables in this file` (true empty state).
2. Library collection with the same name as a local one: separate sections, each with its origin.
3. Variable alias: printed as `→ <target name>` with the resolved value.
4. Hidden-from-publishing variables: included for `scope:file` (they are the file's own) with a
   `(not published)` note.
5. `platform: ios` with no iOS code syntax: falls back to the sanitized name and says so per token.
6. Very large design system (5,000 variables): truncated with markers at `max_tokens`.
