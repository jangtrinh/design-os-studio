## 1. Summary and user story

As a designer (or the variant ranking step), I merge a branch into main: every change the branch made
lands on main, nodes the branch added get fresh ids where needed with every reference fixed, I choose
main or branch per conflicting layer, versions are saved before and after, one undo reverts the whole
merge, and the merged branch is archived (read-only, restorable).

## 3. Behaviour rules

1. Inputs: base (the branch point version), main (current), branch (current); `Diff3` from T10.2 with
   `ours = main`, `theirs = branch`.
2. Resolution input: `Resolution { per_layer: BTreeMap<NodeId, Side>, per_entity: BTreeMap<EntityKey,
   Side> }` with `Side::Main | Side::Branch`. Every conflict must have a choice, else
   `MergeError::Unresolved(list)`. Choosing a side applies all of that layer's conflicting groups from
   that side (per layer, R5.18); non-conflicting groups from both sides always apply.
3. ID remap: every node the branch added whose id is also used on main (an `IdCollision` or any id
   present in main's node map) gets a fresh id from main's allocator; descendants follow. The remap
   table then rewrites, inside the merged result, every reference listed in section 2 (instance
   component, component sources, property values and preferred lists, slot preferred lists, prototype
   destinations, flow start nodes, guide frame ids, comment anchors, library external nodes). Variables,
   collections and styles added on the branch with an id or key already used on main get a new id or
   key (`<key>-branch`, numbered), and bindings and `style_refs` are rewritten.
4. Apply order (one `Command::Batch`): entity changes (collections, variables, styles), then node
   removals, adds (parents before children), moves, property changes, then comments. Each step is
   validated against the evolving document; any failure aborts the whole merge with no change
   (`MergeError::Apply { step, reason }`).
5. Versions: before applying, save an auto version on main labelled `Before merge of <branch>`; after
   committing, save `After merge of <branch>`. The branch status becomes `Merged { into_version }` and
   it is archived (read-only, restorable via T10.1).
6. Undo: one `designos_undo` / Studio undo reverts the merge (the batch); the branch is not
   un-archived by undo (archive is library state; restore is explicit).
7. Validation after merge: every reference in section 2 resolves (no dangling ids); the merge refuses
   to commit otherwise (`MergeError::DanglingReference`).

## 8. Edge cases

1. Branch deleted a component that main used in a new instance: delete-vs-modify conflict on the
   component; choosing `Branch` removes it only if no main instance references it, else
   `MergeError::DanglingReference` names the instances (the user must choose `Main`).
2. Branch added an instance of a component main deleted: the instance would dangle → reported as a
   conflict on the instance (`DependsOnRemoved`).
3. Comment pinned on a node the branch added and remapped: anchor rewritten to the new id.
4. Both added a variable named the same with different ids: both kept; the branch one renamed
   `<name> (branch)` in the report.
5. Main changed since the branch point only in unrelated pages: merge applies branch changes; main
   changes stay.
6. Merge of an archived branch: refused (`MergeError::BranchArchived`).
